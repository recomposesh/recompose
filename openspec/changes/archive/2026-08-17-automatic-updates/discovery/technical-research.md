# Research brief: automatic updates (tier full)

Scope covered: library choice and version, the API surface each spec requirement lands on, the channel-gating primitives, the release-pipeline consequences, prior art for the "no dialog" update affordance, and a testing approach. Repository budget spent at 14 reads; the gaps that budget left are named at the end.

## 1. What the repository already holds

- `docs/adr/0133-an-update-arrives-through-the-channel-that-installed-it.md` (accepted 2026-08-16) already decides the library, the per-channel rule, the two Windows channels, universal macOS, and staged rollout. This brief verifies those decisions against primary sources and surfaces what the ADR does not cover.
- `openspec/changes/automatic-updates/specs/updates/spec.md` carries three requirements: channel-gated updating, a background download with a standing restart affordance and no dialog, and a silent-but-logged failed check with a launch check plus an interval.
- `apps/desktop/electron-builder.yml` already publishes to GitHub (`provider: github`, `owner: recomposesh`), sets `nsis` as the Windows target, and sets `mac.notarize: false`. It declares no `mac.target` (so the electron-builder default `dmg` + `zip` applies), no `win.publisherName`, and no `win.verifyUpdateCodeSignature`. Line 10 already excludes `dev-app-update.yml` from the packaged files, so a dev feed config can sit in `apps/desktop/` without shipping.
- `.github/workflows/release.yml` builds each platform with `--publish never`, copies `*.blockmap` and `latest*.yml` into `release-out/`, attests provenance and SBOM, then a separate `draft` job runs `gh release create --draft`. Nothing signs anything today.
- `apps/desktop/package.json` pins `electron-builder` 26.15.3 (devDependency) and `electron` 43.2.0. No updater dependency exists yet.
- No updater code exists anywhere: a repository-wide grep for `electron-updater|autoUpdater|stagingPercentage|dev-app-update` hits only docs, the ADR, and that one `electron-builder.yml` exclusion line.
- Wiring points: `apps/desktop/src/main/index.ts` is where lifecycle wiring lands, `apps/desktop/src/main/ipc/push-events.ts` holds the main-to-renderer push helpers (`pushSettingsChanged`, `pushLaunchRefused` and friends, all `webContents.send` over every window), and `packages/contracts/src/ipc.ts` holds the `ipcEvents` map that types those payloads (`IpcEvent`, `IpcEventPayload`, `RecomposeIpcEvents`).

## 2. Library: electron-updater, and which version

`electron-updater` is at **6.8.9, MIT**, dependencies `builder-util-runtime 9.7.0`, `semver ~7.7.3`, `js-yaml`, `fs-extra`, `lazy-val`, `lodash.isequal`, `lodash.escaperegexp`, `tiny-typed-emitter` ([registry.npmjs.org/electron-updater/latest](https://registry.npmjs.org/electron-updater/latest)). It must be a **runtime dependency**, not a devDependency, and electron-builder writes `app-update.yml` into the packaged resources itself, so never call `setFeedURL` ([electron-builder auto-update setup](https://mintlify.wiki/electron-userland/electron-builder/guides/auto-update/setup)). The ADR already says this.

**Security floor: pin at or above 6.3.0-alpha.6.** CVE-2024-39698 is a Windows code-signing bypass in `windowsExecutableCodeSignatureVerifier.ts`: the verification command ran in a shell that expanded environment variables, so `verifySignature()` could be tricked into validating a different file than the one downloaded, and an invalid update installed anyway. Patched in 6.3.0-alpha.6 ([GHSA-9jxc-qjr9-vjxq](https://github.com/advisories/GHSA-9jxc-qjr9-vjxq)). An earlier variant of the same check fell to a backtick in a filename ([Doyensec, 2020-02-24](https://blog.doyensec.com/2020/02/24/electron-updater-update-signature-bypass.html)). 6.8.9 clears both. This history is the concrete argument for the ADR's rejection of "ship unsigned with verification off".

**Version-matching trap that will bite the implementer.** The docs site at electron.build documents `master`, which is ahead of the installed electron-builder 26.15.3. The auto-update feature page describes `autoInstallEvent: "manual" | "onQuit" | "onNextLaunch"` (default `"onQuit"`), while the published 6.8.9 typings still expose the boolean `autoInstallOnAppQuit` (default `true`). The enum replaced the boolean in **electron-updater 7 / electron-builder 27**, where `"onNextLaunch"` is opt-in and is planned to become the default in v28 ([electron-builder auto-update docs](https://www.electron.build/docs/features/auto-update/), [jsdocs.io electron-updater@6.8.9](https://www.jsdocs.io/package/electron-updater), [release-notes search summary](https://github.com/electron-userland/electron-builder/releases)). Write against `autoInstallOnAppQuit` for 6.x and treat the docs site as forward-looking.

## 3. Mapping each spec requirement to the API

Verified members of `AppUpdater` at 6.8.9 ([jsdocs.io](https://www.jsdocs.io/package/electron-updater)): `autoDownload` (boolean, default `true`), `autoInstallOnAppQuit` (boolean, default `true`), `autoRunAppAfterInstall` (default `true`), `allowDowngrade` (default `false`), `allowPrerelease`, `forceDevUpdateConfig` (default `false`), `channel`, `currentVersion` (`SemVer`, readonly), `logger` (`Logger`), `requestHeaders`, `disableWebInstaller` (default `false`), `disableDifferentialDownload` (default `false`, NSIS only). Methods: `checkForUpdates()`, `checkForUpdatesAndNotify()`, `downloadUpdate()`, `quitAndInstall()`, `isUpdaterActive()`. Events: `checking-for-update`, `update-available`, `update-not-available`, `download-progress`, `update-downloaded`, `update-cancelled`, `error`, plus `appimage-filename-updated` on Linux ([electron-builder auto-update docs](https://www.electron.build/docs/features/auto-update/)).

- **"Download in the background"** is `autoDownload: true`, the default. Nothing to write.
- **"Open no window and no dialog"**: do **not** use `checkForUpdatesAndNotify()`. Electron's own tutorial and the electron-builder guide both build their happy path on a notification or a dialog ([Electron: Updating Applications](https://www.electronjs.org/docs/latest/tutorial/updates) recommends a dialog with "Restart"/"Later"). Use `checkForUpdates()` and drive your own affordance off the `update-downloaded` event.
- **"MUST NOT restart on its own"**: `quitAndInstall()` is the only self-restart, so simply never call it outside the person's choice. But note `autoInstallOnAppQuit` defaults to `true`, which means a plain quit installs the pending update without the person ever choosing it. That is not a self-restart and probably matches intent, but it is a deliberate decision the spec does not state. Decide it explicitly rather than inherit the default.
- **"The log carries the reason and the feed address"**: `autoUpdater.logger` takes any object shaped `{ debug(message: string): void; info(message?: any): void; warn(message?: any): void; error(message?: any): void }`. **No electron-log dependency is required**; a small adapter over the `console.warn` style already used in `apps/desktop/src/main/index.ts` satisfies it. The feed address is not handed to you by the error object, so log it from your own config rather than hoping it appears in the message.
- **Caution on `error`**: Node throws on an unhandled `'error'` event ([Node events docs](https://nodejs.org/api/events.html#error-events)), and electron-updater's emitter is built on `tiny-typed-emitter`. Attach an `error` listener before any check, and also handle the rejected promise from `checkForUpdates()`. I did not confirm from source whether `tiny-typed-emitter` preserves the throwing behaviour, so treat the listener as mandatory belt-and-braces.
- **"Checks once at launch and repeats on an interval"**: no built-in scheduler; you own the timer. Electron's official `update-electron-app` uses **every ten minutes** as its reference cadence ([Electron: Updating Applications](https://www.electronjs.org/docs/latest/tutorial/updates)). For a public GitHub repo the provider reads `latest*.yml` from the release download URL unauthenticated, so the 5000/hour API limit (roughly 3 requests per check) only applies on the `GH_TOKEN` private path ([electron-builder auto-update](https://www.electron.build/docs/features/auto-update/)). Ten minutes is defensible; hourly is more considerate and equally spec-compliant.

## 4. Channel gating: the two runtime flags

- **`process.windowsStore`** is `true` when the app runs as an MSIX/AppX package and **`undefined` otherwise**, not `false` ([Electron process docs](https://www.electronjs.org/docs/latest/api/process)). Under the repository's `noUncheckedIndexedAccess`/`exactOptionalPropertyTypes` strictness, write the check as a truthiness test on a value typed `boolean | undefined`, and do not model it as `boolean`.
- **AppX is not merely "owned by the Store": electron-updater does not support AppX at all**, and Store packages update through the Store ([electron-builder appx docs](https://www.electron.build/docs/appx/)). So the gate protects against a crash path, not just a redundancy.
- **`process.env.APPIMAGE`**: `AppImageUpdater` reads it, and when it is absent the app is not an AppImage and the update does not proceed ([electron-builder appimage docs](https://www.electron.build/docs/appimage/), [electron-builder#3167](https://github.com/electron-userland/electron-builder/issues/3167)). Gating on it yourself keeps the deb install silent instead of relying on an internal refusal.
- **`isUpdaterActive()`** returns false when the app is not packaged, which is why a dev run needs `forceDevUpdateConfig`.
- **AppImage caveat worth surfacing in the UX**: the updater replaces the AppImage in place via `fs.rename`, so the containing **directory** must be writable (the file itself need not be), and the filename gains the new version, which breaks a person's existing launcher shortcut ([electron-builder#5810](https://github.com/electron-userland/electron-builder/issues/5810), [electron-builder#2964](https://github.com/electron-userland/electron-builder/issues/2964)). The `appimage-filename-updated` event exists so the app can react. The spec's AppImage scenario says only "the app downloads it", so this is a gap the design should answer.

## 5. The biggest risk this feature carries: signing order versus `latest.yml`

This is the finding I would put first in planning, because it is not in the ADR and it silently breaks every Windows update.

`latest.yml` records a sha512 for each artifact, and `.blockmap` describes the artifact's bytes. **Both are computed by electron-builder at build time.** Signing the `.exe` afterwards changes the file and invalidates both, producing the classic `Error: sha512 checksum mismatch` at update time. electron-builder's own troubleshooting insists the artifact and the `.yml` be generated together in the same build ([electron-builder troubleshooting](https://www.electron.build/docs/troubleshooting/), [electron-builder#2111 "Code sign after exe generation - sha512 checksum mismatch"](https://github.com/electron-userland/electron-builder/issues/2111), [#6848](https://github.com/electron-userland/electron-builder/issues/6848)).

SignPath's OSS flow is inherently post-build: you `actions/upload-artifact` the unsigned file, the `submit-signing-request` action submits it with organization/project/signing-policy identifiers, and with `wait-for-completion` (default true, 600 second timeout) it downloads the signed artifact back into the workflow. SignPath verifies that every job up to the signing request ran on GitHub-hosted agents ([SignPath GitHub trusted build docs](https://docs.signpath.io/trusted-build-systems/github), [SignPath/github-action-submit-signing-request](https://github.com/signpath/github-action-submit-signing-request)). The current `.github/workflows/release.yml` has exactly the shape that walks into the trap: build with `--publish never`, then upload artifacts including `latest*.yml`.

Two mitigations, in order of preference:

1. **Sign inside the build via the `win.sign` custom hook.** electron-builder's `sign` property accepts a function or module path that _replaces_ its built-in signtool invocation and receives the file path, cert info, hash algorithm, and a `computeSignToolArgs` helper, explicitly so an external signing service can be plugged in ([Windows code signing docs](https://www.electron.build/docs/features/code-signing/code-signing-win/)). Signing then happens before hashing, and `latest.yml` is correct by construction. The open question is whether SignPath's OSS tier can be driven from inside a hook (its documented path is the GitHub Action, and OSS signing may require a manual approval that no build can block on for 600 seconds reliably).
2. **Sign after the build, then regenerate `.blockmap` and rewrite `latest.yml`.** Community route only; no official electron-builder support. The blockmap tool is invoked as `app-builder blockmap --input=<file> --output=<file>.blockmap --compression=gzip`, and the sha512 in the manifest must be rewritten too ([electron-builder#5267 "Manually regenerate blockmap"](https://github.com/electron-userland/electron-builder/issues/5267), [gist: rebuild zip and update blockmap](https://gist.github.com/harshitsilly/a1bd5a405f93966aad20358ae6c4cec5)). Encoding trap: the manifest sha512 is base64, not hex; a 128-hex-character value in an error message is the signature of a hand-rolled manifest.

**Recommendation**: treat "which side of the hash the signature lands on" as a named acceptance criterion for the Windows channel, and prove it with a real download-and-install of a signed release before calling the feature done. Route 1 if SignPath can be driven synchronously; otherwise route 2 with a regeneration step that runs before `gh release create`.

## 6. Other pipeline facts that check out against primary sources

- **`win.publisherName` is not cosmetic and the ADR is right about it.** `verifyUpdateCodeSignature` defaults to `true`; the resolved publisher name is baked into `app-update.yml` at build time, and at update time electron-updater compares the downloaded installer's certificate subject against it, refusing to install on mismatch. It defaults to the CN extracted from the signing certificate, and **an array is accepted**, which is the documented way to keep old and new certificates both valid across a rotation ([Windows options](https://www.electron.build/docs/win/), [Windows code signing](https://www.electron.build/docs/features/code-signing/code-signing-win/)). Because SignPath signs after electron-builder runs, electron-builder cannot extract the CN itself, so setting `win.publisherName` explicitly is mandatory rather than optional. Consider an array carrying the SignPath Foundation subject so a future certificate change does not strand installed copies.
- **macOS: `dmg` + `zip` both required.** Squirrel.Mac takes the update from the `zip` even for a `dmg` install, and without `zip` no `latest-mac.yml` is produced at all. Default target is `dmg` + `zip`, which `apps/desktop/electron-builder.yml` inherits by declaring no `mac.target`; the risk is a future edit that adds an explicit target list and drops `zip` ([macOS options](https://www.electron.build/docs/mac/)).
- **macOS notarization**: flip `mac.notarize` and supply one of three env sets, `APPLE_API_KEY` + `APPLE_API_KEY_ID` + `APPLE_API_ISSUER` (recommended), or `APPLE_ID` + `APPLE_APP_SPECIFIC_PASSWORD` + `APPLE_TEAM_ID`, or `APPLE_KEYCHAIN` + `APPLE_KEYCHAIN_PROFILE`. Hardened Runtime and entitlements are prerequisites ([macOS options](https://www.electron.build/docs/mac/)). The repository already has `build/entitlements.mac.plist` wired via `mac.entitlementsInherit`.
- **Universal macOS**: expressed as `mac.target: [{ target: dmg, arch: universal }]`. electron-builder's own advice is to build per architecture on native hardware and merge rather than cross-compile, which conflicts with a single `macos-26` matrix leg producing a universal artifact ([macOS options](https://www.electron.build/docs/mac/)). Worth a spike before committing the workflow change.
- **Staged rollout**: `stagingPercentage: 10` is a field you add to the published `latest*.yml` by hand after the build; the updater compares it against a numeric hash of a per-user id. The documented caveat matches the ADR: to pull a bad staged release you must ship a **higher** version, because a plain re-release of the same number leaves already-updated users stranded ([electron-builder auto-update](https://www.electron.build/docs/features/auto-update/), [electron-builder#3499](https://github.com/electron-userland/electron-builder/issues/3499)). Editing a published manifest by hand is itself a release step someone has to own.
- **Draft releases as the gate** holds: the GitHub provider for a public repo reads the published releases feed, so a draft is invisible to it ([electron-builder auto-update](https://www.electron.build/docs/features/auto-update/)).
- **`allowPrerelease` defaults to `true` when the app version itself carries a prerelease component** such as `0.12.1-alpha.1` ([auto-update setup](https://mintlify.wiki/electron-userland/electron-builder/guides/auto-update/setup)). `apps/desktop/package.json` is at `0.3.0`, so today this is inert, but any `-rc` tag would silently change update behaviour.
- **Differential download**: NSIS uses the `.blockmap` beside the installer, and AppImage carries an embedded blockmap. macOS has no differential path, which is the ADR's "downloads the whole application" consequence ([AppImage docs](https://docs.appimage.org/packaging-guide/optional/updates.html), [electron-builder auto-update](https://www.electron.build/docs/features/auto-update/)). `.github/workflows/release.yml` already ships `*.blockmap`, so nothing regresses here as long as the signing-order problem above is solved.

## 7. Prior art for the "no dialog, standing affordance" UX

Electron's official guidance is the opposite of what the spec asks for: it shows a `dialog` with "Restart" and "Later" on `update-downloaded` ([Electron: Updating Applications](https://www.electronjs.org/docs/latest/tutorial/updates)). The spec's model matches **VS Code** instead: download in the background, then surface a persistent, low-priority affordance the person acts on when they choose, with an explicit "restart to apply the update" action, plus policy-controlled `UpdateMode` values of `manual` and `start` that switch off background checking ([VS Code enterprise update docs](https://code.visualstudio.com/docs/enterprise/updates)). VS Code's known failure mode is instructive for acceptance criteria: the pending-update state must survive an ordinary quit and a failed apply without leaving the app unlaunchable ([microsoft/vscode#246809](https://github.com/microsoft/vscode/issues/246809), [#296791](https://github.com/microsoft/vscode/issues/296791)).

Implementation shape in this codebase: add an event to the `ipcEvents` map in `packages/contracts/src/ipc.ts`, push it from a new helper alongside `pushSettingsChanged` in `apps/desktop/src/main/ipc/push-events.ts` (the broadcast-to-all-windows form, not the focused-window form, since the affordance must outlive navigation and appear in every window), and expose the restart as a request channel in `ipcChannels`. The "outlives navigation" requirement argues for holding the pending version in a renderer-level store rather than in route state.

## 8. Testing approach

The repository's rules (`.claude/rules/tdd-bdd.md`: state-based, doubles only at real process boundaries) point to keeping electron-updater at the edge and putting the decision in a pure function. There is direct prior art in `apps/desktop/src/main/index.ts`: `activationPolicyFor(process.platform, process.env)` and `loginItemAvailabilityFor(process.platform, app.isPackaged)` are exactly this shape. A `updateChannelFor(platform, env, windowsStore)` returning something like `'self' | 'store' | 'package-manager'` is unit-testable, mutation-testable, and needs no Electron at all.

For the integration layer, `forceDevUpdateConfig = true` makes the updater read `dev-app-update.yml` from `app.getAppPath()` instead of `app-update.yml` from `process.resourcesPath`, which lets an unpackaged run point at a local feed ([auto-update setup](https://mintlify.wiki/electron-userland/electron-builder/guides/auto-update/setup)). `apps/desktop/electron-builder.yml` line 10 already excludes that filename from packaged files, so the fixture will not ship. The repository's existing `test:e2e:packaged` Playwright project is the natural home for a real feed exercise.

## 9. Recommendation, condensed

Adopt `electron-updater` at `^6.8.9` as a runtime dependency of `@recompose/desktop`, matched to the installed electron-builder 26.x, and read the 6.x API rather than the docs site's v27 surface. Gate on `process.windowsStore` and `process.env.APPIMAGE` in a pure policy function. Drive the affordance from `update-downloaded` with `checkForUpdates()`, never `checkForUpdatesAndNotify()`, attach an `error` listener plus a `logger` adapter, and decide `autoInstallOnAppQuit` deliberately. Treat the Windows signing-order problem in section 5 as a first-class planning item with its own acceptance criterion, since it is the one issue that fails silently in production and is absent from ADR-0133.

## 10. Gaps and conflicts, stated plainly

- **Version pairing is inferred, not cited.** No official page states that electron-updater 6.8.9 is the sanctioned companion to electron-builder 26.15.3. I infer it from the shared `builder-util-runtime 9.7.0` and from the enum change landing in v27. Verify at install time.
- **Sources conflicted on `autoInstallOnAppQuit` versus `autoInstallEvent`**; I resolved it as a version boundary (6.x boolean, 7.x enum) from release-note summaries rather than a single authoritative page. Confirm against the installed typings.
- **SignPath's OSS approval semantics are unconfirmed.** Its docs did not state whether Foundation projects must approve each signing request manually, which decides whether the in-build `win.sign` hook is viable at all. ADR-0133 asserts a manual approval per release; I could not verify that from SignPath's own pages.
- **No official route exists for regenerating `latest.yml` after signing.** Everything found is issue threads and a gist. If route 2 is chosen, it is unsupported ground.
- **Unread, on budget**: `apps/desktop/build/after-pack.cjs` (an `afterPack` hook that may interact with universal merging or with signing), `docs/adr/0035-release-operations.md`, and the renderer side of `packages/contracts/src/ipc.ts` beyond the `ipcEvents` shape.
- **Unresearched**: Microsoft Store certification timelines and the `appx` build requirements beyond "Windows 10 or later host", and whether the Store's `appx` needs a separate `win.publisherName` value (the docs note the same field is also used for AppX/MSIX identity matching, which may collide with the SignPath Foundation value used for NSIS verification). That collision is a plausible conflict between the ADR's two Windows channels and deserves a check before implementation.
