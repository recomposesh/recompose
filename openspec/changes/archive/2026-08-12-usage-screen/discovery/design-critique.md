# Design critique: usage screen (gate 1)

Read-only pass over `proposal.md` against `discovery/mobbin-references.md`, `discovery/locked-decisions.md`, `discovery/approach-ux-first.md`, the shipped renderer, and the macOS Human Interface Guidelines. Findings are input to the maintainer's gate-1 decision and block nothing on their own.

## Verdict

This is a strong design document at the level of data honesty and a thin one at the level of pixels. The two-plane seam, the closed-buckets-only report, the contract shape that forbids cost below day width, and the table twin as the accessibility strategy are all real engineering of trust, and they are the parts most designs of this kind get wrong. What the document does not yet carry is the screen itself: it names five new components and zero new tokens for a screen whose entire novelty is painted magnitude, it specifies a loading state that prints false numbers, it leaves the most-wanted metric (spend) with no defined reading at the default range, and it puts the one time-critical question (am I about to run out of quota) last in reading order, inverting the very Mobbin reference it cites for that section. One premise is also wrong against the build: the "parked" settings retention row does not exist in the shipped app. No screenshots, mockup, or built pixels exist for this feature, so nothing here is judged on taste against an image. Every finding anchors to a proposal section, and where only pixels can settle a question I name the measurement to take in the dual-scheme pass rather than guessing the outcome.

## Ranked findings

### 1. The "parked" settings retention row does not exist in the build

- **Severity:** blocker-candidate
- **Targets:** `Why` (fifth bullet), `Settings`, `Spec conflicts this delta settles` (item 2)
- **Problem:** The proposal says "the settings log-retention row stands parked on exactly this machinery" and "the parked retention row in settings goes live, wired to this field through the shipped save channel". There is no retention row on the settings page. `settings-page.tsx` composes General, Server, Appearance, and Data, and a repository-wide search for "retention" in `apps/desktop/src` returns exactly one hit, in `shared/ui/field-group/field-group.stories.tsx`, which is a kit demonstration and not a shipped row. The settings spec scenario at `openspec/specs/settings/spec.md:131` describes the inert row, so the spec and the build disagree and the proposal inherited the spec's claim. This matters as design, not bookkeeping: "rewire an existing control" is a one-line change, while "design a new destructive control" is a screen decision nobody has made. Two sub-problems fall out. The kit story renders the row as a three-segment `SegmentedControl` (7 / 30 / 90 days), while the proposal specifies "an integer defaulting to 30, bounded to 7 through 90", which the segmented control cannot express. And shortening retention destroys buckets permanently on the next prune ("the prune runs on load and on every flush"), with no confirmation, no undo, and no stated consequence. macOS anti-pattern 11 and Rule 7.2 both bite: a control that irreversibly deletes user data on change needs either a confirmation with a stated consequence or a description that says what is about to be lost.
- **Fix:** State in the delta that the retention row is new, name its section (Data is the natural home, beside the config folder), and pick the control. The shipped precedent for a destructive settings change with a consequence is `RestartConfirmation` in `server-section.tsx`, which holds the change until the person accepts the cost. Reuse that shape: a `SegmentedControl` with the kit's 7 / 30 / 90 segments (matching the bounds already committed), a `description` line that names what shortening drops, and a confirmation when the new window is shorter than the current one and buckets would be pruned.
- **Evidence:** `apps/desktop/src/renderer/src/pages/settings/ui/settings-page/settings-page.tsx`, `apps/desktop/src/renderer/src/shared/ui/field-group/field-group.stories.tsx:90-103`, `apps/desktop/src/renderer/src/pages/settings/ui/server-section/server-section.tsx:174-184`.

### 2. The loading state prints false zeros

- **Severity:** blocker-candidate
- **Targets:** `The screen > Anatomy`, item 6 ("Loading reads zeros from the live plane instead of spinners")
- **Problem:** The footer precedent this borrows from is honest because the footer's window is always live: a zero there is a true statement about the trailing minute. On the usage screen at the default 24h range, and at 7d and 30d, the live plane covers only the trailing hour, so tiles that "read zeros from the live plane" while the ledger answer is in flight print `0 requests` and `$0.00` for a machine that served a million requests, then swap to the truth. That is not an absent reading, it is a wrong one, and it is wrong on every single open of the page. The principle the design already commits to elsewhere ("misses stay visible", "unknown minutes render as gaps, never as zeros" in `approach-ux-first.md:144`) is exactly the principle this violates. Note that the gap-versus-zero guarantee from approach C was dropped in absorption: `proposal.md` says only "the 1h range folds live rows in the renderer" and never restates it.
- **Fix:** Split the two cases the single word "loading" is hiding. A range the live plane genuinely covers (1h) reads zeros, unchanged. A ledger-backed range reads a pending placeholder until the answer lands: the tile keeps its label and its unit and renders the figure as an em-width dash or a skeleton block of the number's own width, so nothing reflows on arrival, and the chart draws its axis and caption with no bars. macOS Rule 7.3 favors inline status over interruption, so an indeterminate indicator in the section header is acceptable and a spinner over the page is not. Restore approach C's gap rule to the proposal text: minutes older than the oldest held row render as gaps labelled unknown.
- **Evidence:** `traffic-footer.tsx:125` and its docstring ("an idle gateway reads zeros instead of hiding") show why the precedent is sound where it is used, and why it does not transfer.

### 3. Spend has no defined reading below day width, and the default range is one

- **Severity:** blocker-candidate
- **Targets:** `Interaction model` (the spend tile's special rule), `The screen > Anatomy` item 2
- **Problem:** Cost exists only at day width by contract shape, which is the right call. But the tiles print "range total" and the default range is 24h, so on first open the Spend tile has no number the contract can supply. The proposal never says what it prints. Worse, the escape approach C reached for makes the range control lie: "selecting Spend always draws day bars over the days that cover the chosen range (a 1h or 24h range draws today plus the six prior days for context)". Selecting a metric silently changes the time window from 24 hours to 7 days while the segmented control still reads 24h, and the tile totals then disagree with the chart totals on the same screen. At the 1h range the day-width chart degenerates to a single bar, which is not a chart. This is the screen's most-wanted metric failing in its most common state.
- **Fix:** Pick one and write it into the delta. Either (a) the Spend tile reads the whole covering days and says so on its face ("today so far" at 1h and 24h), and selecting it moves the range control to a day-width range so the control never disagrees with the chart, or (b) sub-day ranges render the Spend tile as unavailable with its reason named, using the shipped inert-row vocabulary (`FieldRow` renders unavailable controls with a `reason`, and the kit story is the merge gate for that pattern). Option (a) is better for the person and needs one sentence: selecting Spend snaps the range to 7d unless a day-width range is already selected.
- **Evidence:** `approach-ux-first.md:61`; the inert-with-a-reason pattern at `field-group.stories.tsx:84-103`.

### 4. The chart is specified with no colors, and the palette it would borrow is already spoken for

- **Severity:** blocker-candidate
- **Targets:** `Design-system gap analysis`, `The screen > Anatomy` item 3
- **Problem:** The gap analysis lists five new components and zero new tokens. The screen's whole novelty is painted magnitude: a three-segment stacked token series (uncached input, cached input, output), a two-treatment spend series, an errors series, a share meter fill, and a window meter fill. `theme.css` has no series ramp. Every saturated token in it is already bound to a domain meaning: teal is gateway, pink is virtual model, blue is subscription, yellow is api-key, purple is aggregator, coral is local, green is running, red is stopped. Borrowing any of them for a chart series breaks the vocabulary the rest of the app teaches, and on this screen specifically the breakdown table names gateways, providers, and account kinds two regions below the chart, so a teal bar meaning "cached input" beside a teal badge meaning "gateway" is an active collision. "Follow the ghost-graph precedent of design tokens for every painted value" is not a color decision, it is a rule about not hardcoding, and ghost-graph paints only `line-strong` and `ink-tertiary`.
- **Fix:** Name the tokens in the delta and land them in the design project with the components: `--color-series-input`, `--color-series-cached`, `--color-series-output`, `--color-series-cost`, `--color-series-cost-equivalent`, `--color-series-errors`, and `--color-meter-fill`, each a `light-dark()` pair chosen to clear 3:1 against `--color-surface-card` in both schemes, and each visibly distinct from the domain role tints. Add the hatch geometry as tokens too (stroke width, pitch, angle) so one pattern definition serves the chart and any later surface. The house directive is to add the token the design asks for rather than snapping to the nearest existing value, and this is that case.
- **Evidence:** `apps/desktop/src/renderer/src/app/styles/theme.css:37-67`; `pages/home/ui/ghost-graph/ghost-graph.tsx:17-33`.

### 5. The hatch-as-fill cannot pass the 3:1 criterion the proposal writes as acceptance

- **Severity:** blocker-candidate
- **Targets:** `Accessibility acceptance` (bullet 3), `The screen > Anatomy` item 3
- **Problem:** The document promises "bar and meter fills clear 3:1 against the card surface in both schemes" and simultaneously specifies the equivalent-cost series as "a diagonal hatch pattern". A hatch is two colors, and in the gaps the bar is the card surface, so the gap pixels measure 1:1 against the surface by construction. The criterion as written is untestable for that series and will either be quietly dropped at implementation or will fail the dual-scheme pass. Two further risks are real and only pixels can settle them: on the dark scheme a light hatch over a dark surface loses most of its perceived mass, and at small bar widths the pattern reads as noise. Widths are computable now. The page column is `--spacing-column: 720px` minus `px-6` on both sides, so about 672px of plot at the default window, and 432px at the 720px minimum window. Thirty day bars with gaps give roughly 20px and 12px; sixty minute bars give roughly 10px and 6px. A 45 degree hatch at any legible pitch has two or three stripes inside a 12px bar.
- **Fix:** Make the hatch a texture over a solid base rather than the fill itself: paint the equivalent series with a solid tint that clears 3:1 on its own, then overlay the `<pattern>` in a contrasting ink. Every pixel of the bar then satisfies the criterion and the hatch carries the distinction without carrying the contrast. Add a minimum bar width to the design (below it, the hatch is dropped and the legend plus the table twin carry the distinction), and state the pattern's `patternUnits="userSpaceOnUse"` so the pitch does not scale with the bar. Record the two measurements the dual-scheme pass must take: hatched-bar base fill against `--color-surface-card` in both schemes, and hatch legibility at the 30d bar width in the 720px minimum window.
- **Evidence:** `theme.css:89` (`--spacing-column: 720px`), `main/windows/window-options.ts:13` (`minWidth: 720`), `usage-page.tsx:10` (`px-6`).

### 6. The scope-empty state is missing, and the deep links aim straight at it

- **Severity:** blocker-candidate
- **Targets:** `The screen > Anatomy` item 6, `Interaction model`
- **Problem:** Four states are specified: global empty, loading, ledger refusal, route crash. The fifth is the most likely one on this screen and it is absent: the scope you chose has no data in the range you chose. Locked decision 2 puts compact summary cards on the gateway and provider surfaces that deep-link into the pre-filtered page, so the app itself will navigate people into this state whenever a gateway has been idle for the linked range. What renders then is an empty chart, an empty breakdown table, and no explanation, with the cause (a chip in the scope bar) visually unrelated to the emptiness. That is the exact shape rider #108 established as a defect, and the proposal cites #108 as its precedent for the empty state without applying it here.
- **Fix:** Add a scoped-empty state that renders in place of the chart and the table, names the scope in its copy, and offers the recovery ("Nothing served through this gateway in the last 7 days" plus a control that clears the deepest scope level or widens the range). Treat the copy as a frozen-set amendment, which is exactly the process #108 established. Also decide whether the summary card should link at all when its own reading is zero; a card that reads zero and still invites a drill is the cheaper defect to prevent at the source.
- **Evidence:** `Rider positioning` bullet on #108; `rider-ledger.md:39-44`.

### 7. The quota meter reads full on day one and silently rescales its own history

- **Severity:** blocker-candidate
- **Targets:** `Quota and balances`, `The screen > Anatomy` item 5
- **Problem:** The busiest-window denominator is locked and the honesty motive behind it is right (no first-party quota API exists, so no figure may claim official remaining quota). The presentation of it is not yet honest. A meter whose denominator is the maximum of the series it plots has two failure modes and both will be seen in the first week. On a fresh install the current window is the busiest window, so the meter fills to 100% the first time anybody looks, which reads as "you are out of quota" at the exact moment the app is trying to earn trust. And the denominator moves: a new record silently rescales every earlier reading, so a person who burned the same tokens today as yesterday sees the bar drop, which is the meter reporting a change that did not happen. The caption "≈ 62% of your busiest 5-hour window" does not rescue either case, because the reader cannot see what the 100% is or when it happened.
- **Fix:** Keep the locked denominator and change how it is drawn. Print the absolute denominator and its date beside the meter ("≈ 1.2M tokens this window, against your busiest 5 hours: 2.0M on 2026-08-03"), so the scale is a visible fact rather than an invisible one. Mark the current window explicitly when it is itself the record, with copy that says so instead of a full bar that says something else. Consider drawing the record as a marker line on a fixed track rather than as the track's end, which removes the rescaling illusion entirely and keeps the honest reading. Approach C's own cut list ranks this fourth for removal ("if the busiest-window scale reads as too clever, cut the fill bar and keep printed burn plus countdown"), and that fallback stays available.
- **Evidence:** `approach-ux-first.md:104` and `approach-ux-first.md:139`; Firecrawl's quota framing in `mobbin-references.md:14` pairs meters with a knowable cycle boundary, which is what this design lacks.

### 8. The shared formatters cannot print the magnitudes this screen prints

- **Severity:** blocker-candidate
- **Targets:** `The extraction stage` (first bullet), `The screen > Anatomy` items 2 and 4
- **Problem:** The extraction stage moves `compactCount`, `readDuration`, and `pluralized` down to `shared/lib` "so tiles, tables, meters, and the summary cards print units exactly as the footer does", and calls the stage a pure refactor with behavior unchanged. `compactCount` stops at one magnitude: anything above 999 becomes `k` with one decimal and there is no `M` or `B`. A 30-day token total of 45 million prints as `45000.0k`. The footer is right to cap, because it defends a fixed-width strip in a live row, but the usage screen's job is the opposite, and a tile headline is the one number on the screen that should be exact. So either the stage is not behavior-preserving (the footer's formatter grows a magnitude ladder, and the footer's tests change with it), or the usage screen prints nonsense. The proposal has to choose, and it currently claims both. Three further formatting rules are missing entirely. There is no tabular-figures rule, although this screen has a display clock re-deriving tiles on a tick and a countdown that counts down, so proportional digits will make every number jitter; the app already knows the answer and uses `tabular-nums` in `log-row.tsx` and `numeric-field.tsx`. There is no currency rule, so a day that cost four tenths of a cent prints `$0.00` for a machine that did spend, which is the same defect the "misses stay visible" rule already forbids for unpriced models. And there is no statement of which type ramp the readings take, although the house has both a mono ramp (`--text-mono-value`, `--text-mono-caption`, used by the footer and the log rows) and a sans ramp.
- **Fix:** Say in the delta that the extraction is a move plus one deliberate behavior change, with the footer's tests updated in the same stage: a magnitude ladder through `k`, `M`, `B`, and a second exact formatter with grouping separators for tile headlines, where the compact form belongs only in dense cells. Add the number rules: `tabular-nums` on every figure that ticks or sits in a column, right alignment on numeric table columns (the log row's convention), `< $0.01` rather than `$0.00` below one cent, and a stated unit for stored cost that does not truncate sub-cent days. Name the type ramp per region.
- **Evidence:** `pages/gateway-canvas/ui/traffic-footer/footer-readings.ts:13-19`; `pages/gateway-canvas/ui/log-row/log-row.tsx:137,149,152`.

### 9. The quota section is last, which inverts the reference the proposal cites for it

- **Severity:** improvement
- **Targets:** `The screen > Anatomy`, reading order
- **Problem:** Reading order is header, tiles, chart, breakdown table, quota. On a 720px column, quota sits below a five-tile row, a chart with a caption, and a breakdown table, so it is a screen and a half down at the default window height of 780px. The questions a person brings to this screen are not equally urgent: "how close am I to the 5-hour limit" is the only one with a deadline attached, and it is the one this app's subscription-routing audience will open the page for. The proposal's own cited source puts it first: Firecrawl's pattern is "progress meters per pool with resets on copy, current-billing-cycle section above historical usage". The proposal names that reference and then inverts it without saying why.
- **Fix:** Either move the quota strip above the chart (matching the cited reference and the reading order of urgency), or keep it where it is and put a compact quota affordance in the header, so the answer with a deadline is visible without scrolling. If the current order is deliberate, say why in the document, because the next reader will otherwise read it as an oversight.
- **Evidence:** `mobbin-references.md:14`; `window-options.ts:11-14`.

### 10. The range control and scope bar scroll away, and the shell already has the macOS home for them

- **Severity:** improvement
- **Targets:** `The screen > Anatomy` item 1
- **Problem:** The scope chips and the range segments sit in the page body beside the `h1`, inside the scrolling region (`__root.tsx` wraps the outlet in `overflow-y-auto`). This page is two to three screens tall, so a person reading the breakdown table cannot see the range their numbers are for and cannot change it without scrolling back. macOS Rule 3.3 puts view switching in the window toolbar for exactly this reason, and the shell already ships the slot: `AppToolbar` takes a `trailing` node described as "the act the current surface stands at the strip's trailing edge", currently used by the providers route. The house convention is stated in the providers page docstring: "the one way into the catalog stands in the window strip the shell owns".
- **Fix:** Put the range `SegmentedControl` in the window strip through the existing `trailing` slot, so it stays visible and pinned while the page scrolls, and keep the scope chips in the page body where they belong to the content. If the chips must also stay reachable, make the header region sticky rather than duplicating the control.
- **Evidence:** `app/routes/-app-toolbar.tsx:11-16,44`; `app/routes/__root.tsx:137-140`; `pages/providers/ui/providers-page/providers-page.tsx:32-39`.

### 11. Nothing selectable is specified as looking selectable, and the drill-down has no cited precedent

- **Severity:** improvement
- **Targets:** `The screen > Anatomy` items 2 and 4
- **Problem:** Two of the screen's three interactions rest on discoverability the document never specifies. The tiles are "one radio group" with no stated resting affordance, no hover state, and no selected treatment, so five stat cards that look exactly like stat cards are the chart's only selector. The breakdown rows are pressable with no stated affordance either, and pressing a row is not a pattern any cited reference uses: Grok switches grouping with a pivot control and Cursor with a group-by dropdown, so row-press drill-down is an invention here rather than a borrowed pattern. It also collides with two shipped conventions. The logs drawer's rows are listbox options with a row cursor and a copy action, so the app teaches that a data row is selectable and copyable, not a navigation trigger; and the footer's docstring makes selectable text an explicit posture ("it reads as selectable text rather than as a control, so a person can take a reading into a bug report"). A row that is a button cannot have its numbers selected with the mouse.
- **Fix:** For the tiles, adopt the shipped selectable-card language rather than inventing one: `node-card` in `theme.css` already defines hover, active, and `aria-pressed='true'` with a tint border and a glow ring, and the canvas teaches it. State that the selected tile carries the chart's series label too, so the link between tile and chart survives without color. For the rows, keep the numbers selectable and add an explicit drill affordance at the row's trailing edge (a chevron control with its own accessible name, "Break down by virtual model"), or promote the group name itself to the link. Either way the whole row stops being one hit target. Consider adding the group-by control the cited references actually use, since it also answers "regroup without narrowing".
- **Evidence:** `theme.css:516-557`; `pages/gateway-canvas/ui/log-row/log-row.tsx:128-136`; `traffic-footer.tsx` docstring; `mobbin-references.md:10-11`.

### 12. The scope chips carry dismissal semantics on a toggle primitive, and the cascade is invisible

- **Severity:** improvement
- **Targets:** `Design-system gap analysis` (`Chip` reuse), `Interaction model`
- **Problem:** `Chip` in `shared/ui` is a `Toggle` with a pressed state, and its docstring defines it as "one narrowing of a list, which a person turns on and off beside its siblings". The scope chips are a different control: they cannot be off (dismissing removes them), they are never presented unselected, and dismissing one has a cascading effect on other chips. There is no remove affordance in the shipped chip at all. The cascade is the sharper problem: "dismissing a chip removes that level and every level below it", so dismissing the gateway chip silently drops four other chips, and nothing on screen warns that it will. The proposal's own sentence argues against its control choice: "the scope is a hierarchy, not a bag of filters". A row of equal chips is precisely the picture of a bag of filters.
- **Fix:** Draw the hierarchy as a hierarchy. A path control (gateway › virtual model › model › provider › account), where pressing a segment truncates to it, makes the cascade self-evident and is a native macOS picture (the Finder path bar, Console.app). If chips stay, they need their own component rather than `Chip`: a trailing remove control with an accessible name that states the cascade ("Remove gateway scope and the four levels below it"), Delete-key support when a chip has focus (Rule 5.5), and a hover or focus preview that dims the chips about to go.
- **Evidence:** `shared/ui/chip/chip.tsx:14-30`; `Interaction model` paragraph 1.

### 13. Nothing says what the screen does in a narrow window

- **Severity:** improvement
- **Targets:** `The screen > Anatomy` items 2 and 4
- **Problem:** The window minimum is 720px wide with the sidebar taking 240px, so the content area can be 480px and the page column 432px after padding. Five metric tiles then get 86px each, and the breakdown table is asked to hold a name, requests, tokens, a dual-figure spend cell (`$0.42 + ≈ $1.10`), a share meter, and a percentage in the same 432px. Even at the 1120px default the column is capped at 720px, so the breakdown is tight there too. The proposal says nothing about any of it. The app has already solved this once and documented the reasoning: the traffic footer is an `@container` with a fixed drop order and a docstring that names which two cells are last standing.
- **Fix:** Specify the narrowing behavior with the footer's discipline. Tiles wrap to a two-row grid below a named container width. Breakdown columns leave in a stated order, with the name and spend last standing. The chart states a minimum bar width and what happens below it (fewer buckets, not thinner bars). Separately, decide whether this screen should keep `--spacing-column` at all: it is a reading measure, and a five-column data table is not reading. A wider measure token for data surfaces is the honest fix, and adding the token the design asks for beats squeezing the design into the existing one.
- **Evidence:** `traffic-footer.tsx:19-21,131` and its docstring; `theme.css:89`; `window-options.ts:11-14`.

### 14. The screen ships no desktop command surface

- **Severity:** improvement
- **Targets:** `The screen`, `Interaction model` (whole section)
- **Problem:** This is an Electron app on macOS with a real menu bar, and the proposal gives the usage screen no menu items, no shortcuts, no context menus, and no pointer reading on the chart. Rule 1.1 and 1.2 want every screen command in the menu bar with a keyboard equivalent, and the app already ships the contextual pattern: `buildAppMenuTemplate` adds a Gateway menu only when the person is on gateway detail, with accelerators for zoom and a checkbox item for the logs drawer. The usage screen has an obvious command set (range, metric, show as table, clear scope, refresh) and reaches none of it from the keyboard. Rule 6.1 and 6.2 want hover states and right-click menus on interactive elements, and no chart in any of the ten cited Mobbin references lacks a hover reading (the OpenAI entry names the tooltip that splits input and output tokens explicitly). Reading a single bucket currently requires opening a disclosure and scanning a table. One collision is worth deciding deliberately: the View menu binds `reload` and `forceReload`, so Cmd+R on a data screen reloads the renderer rather than refreshing the data, which is the opposite of what a person on a usage screen means by it.
- **Fix:** Add a Usage menu that appears on this route, mirroring the Gateway menu's construction: range items with accelerators, a metric submenu, a checkbox for the table twin, and a Refresh item. Add a hover reading on the chart bars (this needs a popover primitive the app does not yet have, so name it in the gap analysis) and a pointer cursor per Rule 6.5. Add a context menu on breakdown rows with the copy and scope actions. State the Cmd+R decision rather than inheriting it by accident.
- **Evidence:** `main/menu/app-menu-template.ts:128-153,167-179`; `mobbin-references.md:9`.

### 15. The ledger error state has no recovery and desynchronizes the range control

- **Severity:** improvement
- **Targets:** `The screen > Anatomy` item 6, `Quota and balances`
- **Problem:** A read refusal renders an inline card naming the operation "while the page falls back to the live hour". Two things go wrong. The card offers nothing to press, so a transient failure is a dead end until the person reloads the whole app, and the same rider #108 posture that demands copy also demands the state not be terminal. And the silent fallback makes the range control lie: it still reads 24h or 30d while the page shows one hour. The proposal is also silent on the OpenRouter balance failing, which is the most likely network failure on the page (expired or revoked credential), and on any manual refresh for a card whose whole value proposition is a staleness stamp.
- **Fix:** Give the error card a Retry action, and either move the range selection to 1h so the control matches what is drawn, or keep the chosen range and say plainly what is being shown instead. Specify the balance-failure state (the card keeps its last read with its stamp, and names the failure) and give the card a refresh control, which also answers the Cmd+R question in finding 14. macOS Rule 7.3 is satisfied by inline status here, so no alert is needed, but an inline status still needs the action that clears it.
- **Evidence:** `Rider positioning` bullet on #108; `Quota and balances` bullet 4.

### 16. UTC day boundaries will disagree with the local times the rest of the app prints

- **Severity:** improvement
- **Targets:** `The data spine > Folds`, `Out of scope` ("local-calendar day folds")
- **Problem:** Buckets fold on UTC boundaries and local-calendar folds are explicitly out of scope, which is defensible as data. The screen then prints day labels that are not the reader's days. The logs drawer prints local wall-clock time (`servedAt` uses `getHours()`), so on the same machine one surface says a request landed at 08:30 and the other files its cost under the previous day. For anyone far from UTC the entire spend axis is shifted, and "today" on the chart is not today. Nothing in the proposal tells the reader this.
- **Fix:** Either label the axis and the caption as UTC in visible text (cheap, honest, slightly unfriendly), or fold days on the local calendar in main at answer time, which is a report-time transform and not a storage change since hours are already the stored unit. If UTC stays, the caption line that already prints range and bucket width is the place to say it, and the 5-hour and weekly window copy needs the same treatment.
- **Evidence:** `pages/gateway-canvas/ui/log-row/logged-request.ts:18-22`; `The data spine > Folds`.

### 17. Latency is an average here and p95 in the footer, with nothing on either surface saying so

- **Severity:** nit
- **Targets:** `The picked approach` (latency line), `The screen > Anatomy` item 2
- **Problem:** The ledger serves average latency only, which is a reasonable v1 cut. The footer prints p95 for the same machine. A person comparing 412ms in the footer with 180ms on the usage tile will conclude one of them is broken. Approach C had the tile print "avg" as part of its label; the proposal dropped that detail. The phrase "each tile prints its range total" also does not hold for latency (an average is not a total) or for errors (a count whose qualifying line is a rate), which matters because this document is what an implementer will build from.
- **Fix:** Print the statistic on the tile face and in the chart caption ("avg latency"), and consider labelling the footer's reading too so the two surfaces read as different questions rather than different answers. Fix the "range total" phrasing to name what each tile actually prints.

### 18. `$0.42 + ≈ $1.10` reads as arithmetic in a design whose whole point is that the two never merge

- **Severity:** nit
- **Targets:** `Pricing > Basis split`, `The screen > Anatomy` item 2
- **Problem:** The rule is that real cost and equivalent cost stay distinguishable and never combine into one number. The chosen connector is a plus sign, which is the symbol for combining numbers, and a reader will add them. At `--text-caption` size in secondary ink, the `≈` that carries the entire honesty posture is a light two-stroke glyph that is easy to miss, and the app has no existing use of it anywhere to build recognition. The claim that "the prefix is text, so it survives copy-paste and screen readers" is half right: it survives copy-paste, but VoiceOver's announcement of U+2248 depends on punctuation verbosity and cannot be relied on at default settings.
- **Fix:** Drop the plus. Stack the two figures on their own lines with word labels ("billed" and "equivalent"), or separate them with a middot. Give each approximate reading a visually hidden word form so the accessible name says "about $1.10 equivalent" while the visible glyph stays for copy-paste. State the glyph's minimum size and that it takes full ink rather than secondary.

### 19. The retention edge is invisible, so a shortened window reads as a quiet machine

- **Severity:** nit
- **Targets:** `The correctness laws > Retention`, `Settings`
- **Problem:** Retention defaults to 30 days and can be set to 7. The range control offers 30d regardless. With a 7-day window, the 30d range draws 23 empty bars and a breakdown table missing three weeks of history, and nothing on the screen says the data was pruned rather than never earned. The same reading appears after any long idle period once the prune has run.
- **Fix:** Mark the retention edge on the chart (an annotation at the oldest retained bucket, "retained from ...") and either disable range segments beyond the retention window with their reason named, using the shipped inert-control vocabulary, or state the truncation in the caption line.

### 20. Document precision items that will cost time downstream

- **Severity:** nit
- **Targets:** `The data spine > Channels`, `Design-system gap analysis`
- **Problem:** Three small drifts. The third channel is `usage:balances` in the proposal and `usage:aggregator-credits` in the absorbed approach C, and both names appear in discovery. The gap analysis lists "share meter" and "window meter" as two new components when they are one fill primitive with two compositions, which invites two fill implementations and two contrast results. And the gap analysis omits three primitives the design needs: a table shell (the breakdown table and the data-table twin are two tables on one screen with no shared shape), a disclosure, and a popover for the chart hover reading recommended in finding 14.
- **Fix:** Settle the channel name in the delta. State that one proportion-fill primitive serves both meters. Add the three missing primitives to the gap list so their stories and their dual-scheme checks are planned rather than discovered.

## The three things this proposal gets most right

1. **The two-plane seam is a structural guarantee, not a convention.** Reports return closed buckets only, so the live hour and the ledger cannot double count by construction, and the seam is a bucket boundary rather than a timestamp comparison. Most designs of this shape try to reconcile live and stored numbers at read time and quietly disagree with themselves; this one makes the disagreement impossible to express.

2. **The honesty rules are enforced by contract shape rather than by discipline.** Cost fields do not exist below day width, so no component can leak a per-hour cost even by accident. Real and equivalent cost never merge into one field. Unpriced models surface by name and request count instead of as zero dollars. Each of these is the kind of rule that usually lives in a review comment and erodes in six months, and here each is a shape the code cannot violate.

3. **The accessibility strategy is testable, and it names its own test.** "The page still reads complete with the chart's SVG deleted" is a criterion anybody can run in ten seconds, and the data-table twin is a real conformance strategy under the 1.4.11 "available in another form" clause rather than a promise about contrast. The preparatory extraction stage deserves the same credit: moving the reading formatters and the single error authority down before the page consumes them is the difference between one vocabulary and three, even though finding 8 shows the stage needs one deliberate behavior change to carry the new magnitudes.
